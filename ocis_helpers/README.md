# The OCIS envvar Documentation Helpers

This folder contains a set of helpers written in Go, Python and Bash, which are used to automate the creation of relevant environment variable related files for the ocis admin documentation. These helpers must run at minimum in the respective doc version branch whenever a new ocis version is created. It is usually a good idea to start using them before a new stable branch is deployed. You should also run them regularly on master.

Antora automatically copies files generated by helpers during a build run to a defined location for later use.

The (sub)folders in `services` (see [Folder Structure](#folder-structure)) are the source for this process. Therefore, any name change must be reflected in both the helpers and Antora.

## Prerequisites

* You must have go installed.
* You must have Python installed.
* Bash must be available.
* You must have cloned the ocis repo on the same lavel as this repo.

## Process Flow

When creating the ocis admin docs, Antora requires several files to be present that are generated by the helpers. Therefore, documentation must ensure that these files are present and up to date. Otherwise, errors will be thrown due to missing files, or the data will not be in sync with reality.

The steps to keep everything in sync are:

* Regularly use the `service` task in master
* Always use all helpers for a new ocis version
* A Docs build will then copy the generated files to a defined location, where Antora will process them.

## Programs and Scripts

The helpers are (in order of usage):

1. `identify_envvar_placeholder_names.sh`
2. `go run .`
3. `changed_envvars.py`

**ad 1)**\
This Bash script **checks for any non-SemVer usage** of environment variables relating to introduction and deprecation versions. These version placeholders, which are usually text strings identifying a release name, are used when the ocis Dev Team does not know when the relevant environment variable will be added or removed. Running this script makes it easier to identify these environment variables and set the correct version.

**ad 2)**\
This Go program **generates all the envvar related files required** for the documentation. Although you can run all the steps at once, it is _highly recommended_ to run them one by one. The generated files are located in the `services` subfolder unless otherwise defined.

**ad 3)**\
This Python script generates the relevant **added, deprecated and removed** envvar adoc tables. To run the script, you must first change the versions to be compared in the script to ensure the output is correct. A major prerequisite is, that each version to be compared must have an up-to-date `env_vars.yaml` file located in a subfolder of the `ocis_helpers` folder and that all changes are already merged into the relevant version branches.

## Folder Structure

Both folders are managed using constants that can be redefined if necessary. Please note that if the name of the `services` folder is changed, other helpers may also need to be adapted. The intention behind using constants is to make development easier if folder names need to be changed. Changing without a good reason is not adviced.

1. `output` folder
2. `services` folder

**ad 1)**\
This folder is temporarily generated for all go-template files that are created on the fly. These go programs will then be executed and generate the required output which is saved into the `services` folder. If not defined by a flag when using `go run .`, the folder is deleted once the program has finished successfully. This folder is completely ignored using .gitignore.

**ad 2)**\
The services folder has a sub structure that reflects the purpose of the generated files.
```
services
  adoc              (1)
  env-var-deltas    (2)
  extended          (3)
  persistent_files  (4)
  yaml              (5)
```

Please note that all folders are ignored using .gitignore _except_ the `persistent_files`. folder. All other data can be recrated at any time.

* In (1), you will find all the .adoc files representing the environment variables used in the services. This also includes an additional file that collects all global environment variables starting with `OCIS_`. Therefore, the "service name" `global` is a reserved service name and must not be used to name a service.

* In (2), you will find the added, deprecated and removed .adoc files for that specific version.

* In (3), you will find the rendered extended adoc file based on `extended_vars.yaml`.

* In (4), you will find two types of files.
  * **First**, there is the `env_vars.yaml` file that represents all service dependent envvars like in a database. When running the Python script to generate the envvars that have been added/deprecated/removed, this file is being used to compare between versions.\
  Please note that this file is created “chaotically” and currently has no sort order. Although each recreation appears to involve many changes compared to the previous version, only a few of these are real.
  * **Secondly**, there is the `extended_vars.yaml` file. These environment variables are not related to or defined by any service. They are used to parameterise the ocis code on startup.

* In (5), you will find yaml configuration examples for envvars related to a service.

## Notes to the `extended_vars.yaml` File

The `extended_vars.yaml` file is updated when issuing `go run . rogue`.

This file is very sensitive, so you need to make sure you know what you're doing when you change its contents. Do not experiment. A backup of this file has been created. If anything goes wrong, either simply discard the changes or delete the modified file and run the relevant helper again. It will then be recreated from the backup. Ontop, the changes from the execution will be applied.

* These envvars are defined by parsing for `go.GetEnv` in the ocis code.\
Because there is no standardisation in how developers implement this, a lot of knowledge is required to understand the implementation, intention and the interpretation of the changes in the updated file. Note that test ocis code is usually in the `/tests` folder, which is excluded from gathering. However, there may be a requirement for tests in a service directly. This creates an additional entry that needs to be flagged for exclusion.

* The YAML file is **never** overwritten except the `foundincode` key, but rather extended by environment variable data found in the code.\
Therefore, you must check for validity and manipulate any updates generated manually before generating the adoc file from it. The resulting adoc file is renderd as it is. No more validation is made.

* Please note that new folders are occasionally added to the ocis repository that do not need to be included in the gathering.\
These folders can be excluded via the `exclude_paths` constant in the `extractor_extended_env.go` code. As a rule of thumb, any successful change to the YAML file should be reflected in the `extended_vars.yaml.do_not_delete` file to make it easier to recover the file in case of accidental deletion or corruption. This recration is done automatically if the file is missing in the `envvars` folder!

* A change is triggered in three cases on folders parsed:
  * `go.GetEnv` code is identified 
  * The line number of an existing `go.GetEnv` has changed because of code changes
  * A formerly added block is no longer "valid" because the rawname key is no longer present

Example block:
```
- rawname: _registryEnv
  path: ../../ocis/ocis-pkg/registry/registry.go:88
  foundincode: true
  name: MICRO_REGISTRY
  type: string
  default_value: nats-js-kv
  description: 'The Go micro registry type to use. Supported types are: ''memory''
    and ''nats-js-kv'' (default). Only change on supervision of ownCloud Support.'
  do_ignore: false
```

The above snippet shows the structure, as well as the tasks required for manual manipulation:

* The `do_ignore` key is very important.\
If this key is set to `true`, the follow-up process will add it to the extended .adoc file that is generated. It will then show up in the docs.\
If there are multiple similar blocks with the same `rawname` key, only one should be set to true and configured. The others must not be removed, but set to `false` to exclude them from further processing.

* The `foundincode` key indicates whether `rawname` (a block) has been removed from the ocis code.\
If the result is `false`, check for a configured block with the same `rawname` where just the `path` key differs. If one is found, update from the found block the line number respectively the `foundincode` key. Then remove the block with `foundincode false`.

* While `rawname` defines the variable used internally in the code,\
`name` defines the environment variable that is used to configure ocis. Somtimes, but not always, it is directly defined via `go.GetEnv`.
  * Please note that a developer can use a variable for the name which requires in-depth investigation what the environment variable name is.
  * If the name is "strange", check with the development team whether this environment variable should be excluded from the documentation.

* The `type`, `default_value` and `description` fields cannot be populated automatically. You must check with the development team which values to provide.
* The `path` key indicates the file and line number where this environment varaible has been found.
  * If this environment variable's line number has changed within the same file, a new block is added because the helper cannot distinguish the cause. Therefore, a manual check of the ocis code is required to identify the valid block. Once the correct line number has been identified, simply update the line number of the block with populated values and remove the added block.
  * If the environment variable has been found in multiple files, set `do_ignore` to `true` in all duplicate blocks except the one containing populated values. Do not delete the blocks — they will be regenerated on the next run with `doingnore false`!

* After fixes have been applied, you **must** re-run the rogue helper to check that the fixes were successful. You will know if it was successful if formerly added blocks are not added again.


### Tasks After any File Changes

Once all changes have been completed, the following tasks needs to be carried out:

* Run `go run . extended` to generate the adoc files for extended environment variables. Check the result.
* Copy the contents of the updated `extended_vars.yaml` file to `extended_vars.yaml.do_not_delete`\
This will make life easier when the file is accidentally corrupted or deleted for that version, as it will allow you to recover it.

### Recovery

If the `extended_vars.yaml` file has been corrupted or accidentally deleted, it can be recovered. Simply discard the changes or delete the corrupted version. The Go code will then check for its absence and recover it on the next helper run using the extended task. Any changes will then be applied to the recovered file. **IMPORTANT**: Both files MUST be present in a version branch!

## Helper Usage

* Please note that the `ocis_helper` directory **MUST** be included in the version you are working on for the documentation to be available. Backport it from `master` if it is missing!
* **IMPORTANT**: The version branches that you are working on must be the same in both the documentation and the ocis repository. **DO NOT MIX VERSION BRANCHES**.\
Examples:
   ```
   docs      ocis
   
   master    master       OK
   8.2       stable-8.2   OK
   master    stable-8.2   WRONG
   ```

**First switch to the relevant branches in both repos. The versions must match!**

As there may be changes to Go dependencies during development or between versions, updating the Go dependencies may be necessary. When running `go run . <task>`, you will be notified by the following message: `go: updates to go.mod needed; to update it`. Run `go mod tidy` to update the dependencies for this version. These changes are tracked and must be committed and merged for that version. This is one of the reasons why versions must match.

* In `master`, dependency changes may happen from time to time.
* In a `version`, dependency changes will most likely happen when creating the stable branch for that version. Usually, there will be no dependency change for this version post creating the branch, but this is not guaranteed.

### Branch Dependent Tasks

The way in which the helpers are used differs slightly depending on which version branch they are used in.

**IMPORTANT** Before using any helpers, create a working branch based on the branch to which you want to apply the changes.
 
#### In the Master Branch

The following tasks are done in `master`:

* Regulary run `go run . services`, especially when there are changes to environment variables in the ocis repo.
  * This will create all service dependent adoc and yaml files for environment variables.

* **Before** a new `stable-x.y` is created:
  * Use the `identify_envvar_placeholder_names.sh` script to check if any environment variables need to be updated to regular SemVer for the upcoming stable release.
    * Please note that the version to be set must be in the format `<major>.<minor>.0`.\
    The patch release is always set to 0 (zero)! Any issues found must be updated in the ocis repo immediately - before the stable branch is created.
    * Please note, that before you can continue, the changes in ocis must be merged and backported to the stable branch if required! 
  * `go run . services`
  * `go run . rogue` and `go run . extended`\
  These tasks will catch all envvars that are not defined in a service and create the adoc file from it.\
  Careful follow the [Notes to the `extended_vars.yaml` File](#notes-to-the-extended_varsyaml-file) to complete this task.

* Please note that any environment variables that have been added, deprecated or removed are not part of the master branch. If data is shown in the documentation, it probably refers to the most recent stable version branch.

* Before merging the changes, a docs build **must** be issued to ensure that all changes are picked up by the Antora build process and are copied into the necessary directory. If this step is not taken, the changes will not be visible in the documentation and/or errors will be shown.

#### In a Version Branch 

* The version branch must be checked to see if the `identify_envvar_placeholder_names.sh` script has missed anything or developers have added changes that are not covered.
  * To do so, re-run the script. If it finds any envvar with a non-compliant SemVer set, proceed as described in the master branch description above.
  * Please note, that before you can continue, the changes in ocis must be merged and backported to the master branch if required!

* Continue to redo the additional steps from the _Before_ block above. This ensures nothing gets missed or overseen.
  * The `services` tasks is important to be issued and can be run at any time if for example a new envvar is changed in ocis master and backported to this version branch. By doing so, the `env_vars.yaml` file will be updated which is the basis for added/deprecated and removed envvars.
  * The `rogue` task can be used, but this is not essential. Extended envvars should not be changed after a stable branch has been created from the master branch. If a change is recognised, follow the above description to complete it.

* Before merging the changes, a docs build **must** be issued to ensure that all changes are picked up by the Antora build process and placed in the correct directory. If this step is not taken, the changes will not be visible in the documentation.
  * **IMPORTANT**
    * The process requires that all `env_vars.yaml` files compared are up-to-date.
    * To generate `added, deprecated and removed` files, the process accesses the version branches on GitHub, rather than locally. This is because the helper itself runs in a version branch and saves the results which must not be switched during processing.

* See the next section on how to generate `added, deprecated and removed` envvar adoc files.

Please note that whenever a change is applied to the ocis stable branch that affects environment files, the procedure needs to be redone!

## Envvar Delta File Creation

To create the `added, deprecated and removed` environment variables adoc files for a version, the following prerequisites must be met and steps must be taken:

* All versions compared must have an actual `env_vars.yaml` file merged in the respective version.  

* Check the versions set in the `changed_envvars.py` script and adapt if required.
  * Any changes of the script must be part of the commit. Which eases a possible post-merge re-run.

* Run the `changed_envvars.py` script.
  * This will create the required files in the `services/env_var_deltas/` subfolder.
  * Use the `-d` flag (dryrun) beforehand to check if additional exclusion from backported introduction versions need to be applied. If the `TO` version is e.g. `8.1.0` but you also find `8.2.0` entries, you need to exclude them additionally in `extraExcludePattern` (not in `defaultExcludePattern`).
  * Note that if placeholders are found that have not been catched with the bash script or if there are patch releases for introduction versions other than `0` (zero), you must fix them in the ocis branches (plural) first and recreate + merge the changed `env_vars.yaml` file before restarting.

* Adapt the content of the output:
  * Replace, if present, `xxx` with the appropriate service name.\
    Consider that the string for `xref` needs to be all lower letters while the printed name starts with a capital letter.
  * Group all envvars that belong to the same service and remove the xref directive  for all but the first. This makes reading much easier.

* Before merging the changes, a docs build **must** be issued to ensure that all changes are picked up by the Antora build process and placed in the correct directory. If this step is not taken, the changes will not be visible in the documentation.

Note that on any consecutive script run, any changes made are overwritten and you need to re-apply them!
